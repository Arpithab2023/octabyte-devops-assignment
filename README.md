# Octa Byte AI — DevOps Assignment

End-to-end infra provisioning, CI/CD, monitoring/logging and documentation for a
containerized web app + PostgreSQL backend on AWS.

## Architecture

```
Internet
   │
   ▼
[ ALB (public subnets) ]  ── HTTP/HTTPS, SG: 80/443 from 0.0.0.0/0
   │
   ▼
[ ECS Fargate service (private subnets) ]  ── SG: container port from ALB only
   │
   ▼
[ RDS PostgreSQL (private DB subnets) ]  ── SG: 5432 from app tier only
```

- **VPC**: 1 VPC, 2 AZs, public / private-app / private-db subnet tiers.
- **Compute**: ECS Fargate (chosen over raw EC2 — no AMI/patching overhead, scales
  faster, matches how the CI/CD pipeline ships containers).
- **Database**: RDS PostgreSQL, Multi-AZ toggle via `db_multi_az` variable
  (off by default to save cost in staging, on for production).
- **Load balancing**: Application Load Balancer with target-group health checks
  on `/health`.
- **Secrets**: DB credentials generated by Terraform (`random_password`) and stored
  in AWS Secrets Manager — never written to `.tf` files or plain outputs. The ECS
  task pulls them at container start via the `secrets` block in the task definition.
- **Autoscaling**: ECS target-tracking policy on CPU (60%) — beyond the minimum ask,
  included so the service handles load spikes without manual intervention.

## Setup & run

### 1. Prerequisites
- Terraform >= 1.5, AWS CLI configured with an account that can create VPC/ECS/RDS/IAM resources
- Docker (for local build/test)
- An AWS account with an OIDC identity provider configured for GitHub Actions
  (avoids long-lived AWS keys in CI — see `AWS_DEPLOY_ROLE_ARN` secret)

### 2. Bootstrap remote state (once)
```bash
cd terraform
./bootstrap-backend.sh          # creates S3 bucket + DynamoDB lock table
# then edit versions.tf: set the bucket name it printed
```

### 3. Provision infrastructure
```bash
terraform init
terraform plan -out=tfplan
terraform apply tfplan
```

### 4. Wire up CI/CD
- Push this repo to GitHub.
- Add repo secrets: `AWS_DEPLOY_ROLE_ARN`, `SNYK_TOKEN`, `SLACK_WEBHOOK_URL`.
- Create two GitHub **Environments**: `staging` (no protection) and
  `production` (required reviewers) — this is what implements the manual
  approval gate in Part 2.
- Open a PR → triggers `test` + `dependency-scan`.
- Merge to `main` → builds image, scans it (Trivy), pushes to ECR, deploys to
  staging automatically, then **pauses for approval** before production.

### 5. View monitoring & logs
- CloudWatch → Dashboards → `octabyte-infrastructure`, `octabyte-application-health`
- Alarms notify the SNS topic (`alert_email` variable) on CPU/memory/error-rate/latency/storage thresholds.
- **Application logs**: CloudWatch Logs → `/ecs/octabyte-app`
- **System/container metrics**: ECS Container Insights (enabled on the cluster)
- **Access logs**: ALB access logs land in the S3 bucket from the `alb_access_logs_bucket` output, under `alb/AWSLogs/<account-id>/...`, auto-expired after 60 days

## Security considerations
- All app and DB resources sit in private subnets; only the ALB is internet-facing.
- Security groups are scoped tier-to-tier (ALB→app→DB), no wide-open ports beyond the ALB's 80/443.
- Secrets never touch source control or Terraform state outputs in plaintext — Secrets Manager only.
- ECR image scanning on push + Trivy scan in CI blocks deploys with critical/high CVEs.
- CI/CD uses GitHub OIDC → short-lived AWS role assumption, not static access keys.
- RDS storage encrypted at rest; not publicly accessible.
- Container runs as a non-root user (see `Dockerfile`).

## Cost optimization measures
- Single NAT Gateway (not one per AZ) — acceptable for staging/assignment scope;
  documented trade-off (loses HA if that AZ fails) with a one-line change to fix for prod.
- Fargate + autoscaling means you pay for actual usage, not idle EC2 capacity.
- `db.t4g.micro` + Multi-AZ **disabled** by default; flip `db_multi_az` for production.
- CloudWatch log retention capped at 30 days instead of indefinite.
- ECR immutable tags avoid storing/duplicating redundant image layers via careless overwrites.

## Backup strategy
- RDS automated backups, 7-day retention (`db_backup_retention_days`), plus a
  final snapshot on destroy (`skip_final_snapshot = false`).
- Point-in-time recovery is implicitly available via automated backups.
